User guide

Verify reproducibility

Compliance auditors and supply-chain reviewers can take the published Eliya source, run the documented build, and produce a tarball that is byte-for-byte identical to the one Asymm signed and published. This page documents the build-twice ceremony, the five reproducibility layers Eliya eliminates, and the exact commands to run.

Why reproducibility matters

A signed release proves the signing key was used; it does NOT prove the binary corresponds to the published source. Reproducibility closes that gap: if the published source rebuilds bit-identical to the signed binary, then the binary has no patches beyond what the source repository carries. For compliance-conscious deployments, that's the difference between "we trust Asymm" and "we can independently confirm."

Eliya is engineered for byte-identical rebuilds, not merely "best-effort similar." The build chain is locked at every layer that would otherwise introduce nondeterminism — timestamps, archive metadata, toolchain versions, environment paths, even the bundled compression library.

The build-twice ceremony

The verification is a comparison: build Eliya from source twice and confirm the two outputs are byte-identical. Run on the same machine for a within-image rebuild test; run on independent machines (different hardware, different operators, fresh OS) for cross-environment confirmation.

Prerequisites

  • Docker (the build runs inside a pinned eliya-jdk-buildenv container per ADR-00023; the host needs only Docker + git + standard CLI tools)
  • ~30 GB free disk space for the build tree
  • ~2-3 hours for one full build on a 4-core machine; ~60 min on 16-core
  • The published mirror repository tag for the release you want to verify (eliya-jdk-25.0.3 for the first signed GA)

One-shot recipe

# Clone the platform repo (the orchestration layer):
git clone https://github.com/asymmsystems/eliya-jdk-platform
cd eliya-jdk-platform
git checkout eliya-jdk-25.0.3

# Enter the build environment (pulls the digest-pinned buildenv image):
make buildenv-shell

# Inside the container, do build A:
. scripts/env-jdk25.sh
make dev
sha256sum build/openjdk-src/build/*/bundles/eliya-jdk-25.0.3-linux-x64.tar.gz

# Record hash A. Then clean and rebuild:
make clean-all
make dev
sha256sum build/openjdk-src/build/*/bundles/eliya-jdk-25.0.3-linux-x64.tar.gz

# Hash B must equal hash A (and equal the published SHA256SUMS.txt entry).

If hashes differ — how to diagnose

Use diffoscope to identify what changed:

diffoscope build-a.tar.gz build-b.tar.gz

Or, lighter manual chain:

tar tvf build-a.tar.gz | diff - <(tar tvf build-b.tar.gz)
find . -type f -exec sha256sum {} + | sort # per-file listing

If your two rebuilds differ but match each other across multiple runs, the difference is introduced by your environment (toolchain drift, host glibc mismatch, missing devkit pin). Confirm the buildenv image digest matches the one published in scripts/env-jdk25.sh. If runs differ from each other, you've found a reproducibility regression in Eliya — report to security@asymm.systems.

The five reproducibility layers Eliya eliminates

Without explicit countermeasures, an OpenJDK build embeds nondeterministic state at five layers. Eliya locks each:

LayerWhat would varyEliya countermeasure
1. Build-embedded timestamps Build date strings burned into version banners, JAR manifests, class files --with-source-date=${SOURCE_DATE_EPOCH} sourced from git log HEAD time in scripts/common.sh; identical inputs produce identical timestamps
2. Archive metadata tar/gzip headers carry file modification times, owner UIDs, hostname-of-builder Deterministic tar --sort=name --owner=0 --group=0 --numeric-owner + gzip -n (suppresses original filename + timestamp header)
3. Toolchain / environment drift Different GCC versions, different sysroots, different host glibc produce different machine code Pinned eliya-jdk-buildenv image (by SHA digest, not tag) + GCC 14 devkit + per-arch sysroot (Oracle Linux 6.4 for x86_64, 7.6 for aarch64) per ADR-00023
4. Build path / user / hostname Debug info embeds the absolute build directory path; __FILE__ macros expand to absolute paths Normalised inside the container: build directory is always /work, user is always root, no host-specific paths leak in
5. Bundled zlib OpenJDK linked against system zlib produces different compressed output if system zlib version differs across hosts --with-zlib=bundled forces use of the in-tree zlib copy; DEFLATE output stays stable across buildenv image rebuilds

Each layer is a documented engineering decision with rationale in the build orchestration repository's scripts/common.sh, scripts/env-jdk25.sh, and the build-system configure flags. The full architectural rationale is in the corresponding internal ADR (ADR-00023 sec.7) and is summarised here in operator-facing terms.

Confirmed reproducibility level (as of first signed GA)

  • ✓ Within-image reproducibility: two clean builds in the same buildenv container produce bit-identical tarballs. Confirmed 2026-06-02 and 2026-06-05 (both arches).
  • ✓ Cross-image-rebuild reproducibility: two builds across separate buildenv image rebuilds (with docker rmi + make buildenv-image in between) produce bit-identical tarballs. Confirmed 2026-06-05.
  • ✓ Cross-host reproducibility: builds on different physical machines (different CPUs, different OS) with the same buildenv image digest produce bit- identical tarballs. Empirical confirmation across multiple operators is the next milestone.

Comparing against the published binary

After your local build completes, fetch the published SHA256SUMS.txt from the GitHub Release page and compare:

curl -sLO https://github.com/asymmsystems/eliya-jdk/releases/download/eliya-jdk-25.0.3/SHA256SUMS.txt
grep eliya-jdk-25.0.3-linux-x64.tar.gz SHA256SUMS.txt
# Compare with your local build's sha256sum output. Hashes must match.

A match is the proof: the published binary corresponds exactly to the published source. A mismatch is investigative — either your build chain is missing a pin (check buildenv digest, GCC version, devkit version against the values in scripts/env-jdk25.sh), or there's a reproducibility regression to report.
