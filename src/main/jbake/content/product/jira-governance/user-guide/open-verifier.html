Open Verifier Guide

Open Offline Verifier

The open verifier checks LedgerSeal evidence records and FourRealities evidence reports on your own computer. It needs no network and no access to Jira or to the apps. It uses only the Node.js standard library, so an auditor can read every line before running it.

1. Who this guide is for

Auditors, compliance teams and security engineers who receive evidence from a Jira site that uses LedgerSeal or FourRealities, and want to check it without trusting the app that made it.

2. Get the verifier

  • Repository: asymmsystems/jira-governance-code-cli on GitHub, Apache-2.0.
  • Requirement: Node.js 18 or later. No npm packages: the scripts import only node:crypto, node:fs, node:path and node:url.
  • LedgerSeal: verify-evidence.mjs, from release v1.3.0.
  • FourRealities: verify-fourrealities-report.mjs, which comes with version 1.4.0 of the verifier in the same repository. It uses the canonical JSON code of verify-evidence.mjs, so keep both files in the same folder.
  • Keys: the keys/ folder holds the public keys. The Signing keys page lists them with their fingerprints.

Run node verify-evidence.mjs --self-test to check the canonical JSON code against the published test vectors. It prints "PASS n of n vectors".

3. Check a LedgerSeal evidence record

Get the record

  1. Open the sealed issue and its Approval Seal panel.
  2. Open Certificate & attestation details and choose Show evidence (JSON).
  3. Copy the JSON into a file, for example PAY-29-evidence.json.

Run the check

node verify-evidence.mjs PAY-29-evidence.json
node verify-evidence.mjs --evidence PAY-29-evidence.json --public-key ls-prod-2026-11.pub.pem

Without a key file, the verifier reads keys/<keyId>.pub.pem next to the script, using the key id named in the evidence.

Expected output

PASS snapshot hash
PASS history chain (3 entries)
PASS attestation names the newest seal
PASS attestation status matches the history (SEAL_VALID)
PASS signature (ls-prod-2026-11)

A failed check prints FAIL on its line. The verifier always runs all five checks, so one run shows every problem.

CheckPasses when
1. Snapshot hashThe SHA-256 of the canonical JSON of the snapshot equals the snapshot hash in the attestation.
2. History chainThe entries run 1, 2, 3 with no gap; each entry names the hash of the entry before it (the first names 64 zeros); each entry hash is the SHA-256 of that entry.
3. Newest sealThe attestation names the certificate of the newest seal entry.
4. StatusThe attestation status matches the newest entry that is not a redaction: SEAL_VALID for a seal, SEAL_BROKEN for a change, SEAL_REVOKED for a revoke.
5. SignatureThe Ed25519 signature verifies over the canonical attestation with the public key.

NOTE lines. Records made before LedgerSeal used party tokens were converted once; the history then holds a redaction entry, and the verifier names it in a NOTE line. A NOTE also says that the parties map (token to account id) is not signed. A NOTE is not a failure.

Canonical JSON means object keys sorted at every level, no whitespace, and undefined fields left out.

4. Check a FourRealities evidence report

Get the files

  1. In the project, open Four Realities > Evidence reports and choose Download on a Ready report.
  2. Save the report JSON, the report CSV and the signed manifest. The people file is not signed and is not needed for the check.
  3. To check the chain, also keep the manifest of the previous report of the project.

Run the check

node verify-fourrealities-report.mjs <manifest.json> <report.json> <report.csv> [--previous <previous-manifest.json>]

Without a key file, the key is read from keys/<keyId>.pub.pem. You can also give a public key file after the three report files.

CheckPasses when
1. File hashesThe SHA-256 and the byte count of the report JSON and the report CSV equal the values in the manifest.
2. SignatureThe Ed25519 signature verifies over the canonical JSON of the manifest without its signature, with the key named by the manifest.
3. HeaderThe header of the report JSON equals the manifest without its file list, key id and signature.
4. Chain (with --previous)The manifest names the previous report and the SHA-256 of its manifest. A removed report shows as a break.

The verifier also checks the manifest format and that the period is two dates in order, and prints the period with both days included, for example NOTE period 2026-10-09 to 2026-11-07, both days included (UTC).

WARN lines

  • Issues not in the report. When some issues of the scope are not in the report (deleted, no longer readable, or moved to another project while the report was made), the verifier prints a WARN line with their number, which the manifest signs, and one line per issue with its key and the reason. It fails when the report JSON lists a different number. A PASS with such lines means the files are intact, not that the report holds every issue. Check those issues in Jira before you sample.
  • Development key. A report signed with a development key (a key id with -dev-, such as fr-dev-2026-11) prints a WARN line: it is a test report, not evidence from a production site. Such a report that says it is from production fails.

An unsigned report fails the signature check.

What a pass means

The three files are the ones FourRealities signed, and, with --previous, the report follows the previous one. It does not mean that the report holds everything Jira ever recorded: FourRealities reports what Jira's changelog held when the report was made, free-text fields show only that they changed, and the gate results are observed when the report was made. FourRealities is not an administrative audit log: Jira's audit log and Atlassian Guard keep it.

5. Exit codes

  • 0: every check passed. WARN and NOTE lines do not change this.
  • 1: at least one check failed. The FAIL lines name which.
  • 2: a missing argument or file. The verifier prints the usage line, "No evidence file", "No file" or "No public key file".

You can run the verifier in a pipeline and act on the exit code.

6. What a signature does not prove

A pass shows that the files were not changed after they were signed, and that they were signed with the private key of the public key you used. Asymm Systems holds the signing keys. Someone who can rewrite the app's stored data, including the vendor, could write a new consistent record and sign it. The evidence covers only what the app recorded.

7. Keys

Key idUsed by
ls-prod-2026-11LedgerSeal, production (the Marketplace app)
ls-dev-2026-11LedgerSeal, development builds only
fr-prod-2026-11FourRealities evidence reports, production (the Marketplace app)
fr-dev-2026-11FourRealities evidence reports, development builds only

Accept a record as production evidence only when it is signed with a production key. The fingerprints are on the Signing keys page. To check a fingerprint, run openssl pkey -pubin -in key.pem -outform DER | sha256sum.
