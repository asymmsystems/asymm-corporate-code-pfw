DefinitionGuard Guide

DefinitionGuard User & Administrator Guide

How to define and enforce Definition of Done (DoD) criteria with mandatory proof links, non-assignee peer review rules, audited waivers, workflow transition gates, and compliance audit exports.

1. The Ungated Done Problem

Agile teams rely on Definition of Done checklists to ensure code quality, unit test coverage, security reviews, and documentation standards. However, in native Jira or generic checklist plugins, checklists operate on the honor system: assignees tick their own boxes without attaching proof, skip peer reviews when under release pressure, and drag tickets into Done without technical verification.

DefinitionGuard turns the Definition of Done into enforceable code. Checklists are defined per issue type, require mandatory evidence links (such as pull request URLs or test reports), enforce non-assignee peer review rules, and physically block the Jira workflow transition into Done until every requirement is fulfilled or formally waived with an audited reason.

2. Operating the DoD Checklist on an Issue

When working on a Jira issue:

  1. Open the issue panel to locate the DefinitionGuard Checklist.
  2. Review the criteria configured for this specific issue type (e.g. Story vs Bug vs Task).
  3. For standard items, click the checkbox to mark the criterion as satisfied.
  4. For items configured with mandatory evidence, a modal prompts you to enter a verified URL link (e.g. Git PR, SonarQube dashboard, Confluence architecture spec) and an optional note.

3. Non-Assignee Peer Review Enforcement

Compliance standards such as SOC 2 (CC8.1) and ISO 27001 (A.8.32) mandate separation of duties. DefinitionGuard includes an automated non-assignee reviewer rule:

  • When enabled on a criterion (e.g. Code Review Sign-off or QA Acceptance), the ticket assignee is blocked from ticking the box.
  • Only another team member who is not the assignee can verify and complete the item.
  • Every completed item records the verified user account ID and ISO-8601 timestamp in the immutable audit trail.

4. Audited Waivers

When an emergency release or edge case requires skipping a mandatory DoD item:

  1. An authorized team member clicks Waive Item.
  2. A mandatory justification dialog requires a documented explanation (e.g. Hotfix emergency: security team granted 24-hour testing deferral per INC-402).
  3. DefinitionGuard records the waiver, the authorizing user, timestamp, and justification reason.
  4. The item displays a distinctive amber waived lozenge, maintaining full audit visibility without stopping emergency deployments.

5. Workflow Transition Gate into Done

DefinitionGuard includes a native Jira Cloud Workflow Validator that physically gates transitions:

  1. In Project Settings > Workflows, edit your workflow draft.
  2. Select the transition into Done (or your terminal release status).
  3. Add the DefinitionGuard Validator.
  4. Choose whether to enforce 100% item completion, require evidence links, or reject unresolved waivers.
  5. Publish the workflow.

If an engineer attempts to drag an issue to Done with unfulfilled or incomplete checklist criteria, Jira rejects the transition with a descriptive error:

6. Project Settings & Checklist Configuration

Project administrators can customize DoD requirements without touching Jira workflow schemes:

  1. Navigate to Project Settings > DefinitionGuard.
  2. Select the issue type to configure (e.g. Story, Bug, Spike, Epic).
  3. Add, edit, or reorder checklist criteria.
  4. Toggle requirements:
    • Mandatory: Issue cannot transition to Done without this item.
    • Require Evidence: Requires a valid URL link.
    • Non-Assignee Reviewer: Requires verification by someone other than the assignee.

Figure 4: Project settings editor for defining per-issue-type DoD criteria and validation rules.

7. Audit History & Evidence Export

For internal audits and external compliance reviews (SOC 2, ISO 27001), DefinitionGuard provides an exportable JSON audit record:

  • Click Export Audit Record (JSON) on any issue panel.
  • The JSON export contains the complete chronological event stream: who ticked each box, what evidence URL was attached, who approved waivers, and exact timestamps.
  • All data is stored inside customer tenant Forge KVS and can be archived alongside release tags.
