FourRealities Guide

FourRealities User & Administrator Guide

FourRealities shows, for each Jira issue, which delivery evidence exists: a decision record, a complete Definition of Done, a merged pull request and an approval seal. The project dashboard shows where evidence is missing and what to do next. Evidence reports give an auditor one signed file set for a project and a period.

1. Who this guide is for

  • Delivery leads and team members who close evidence gaps. Read sections 3 to 5.
  • Project and Jira administrators who decide Code exceptions and make evidence reports. Read sections 5 and 7.
  • Auditors who sample changes. Read section 7 and the open verifier guide.
  • Jira administrators who install the app and set the evidence sources. Read sections 2, 6 and 11.

2. Install and first setup

  1. Install (Jira administrator). In Jira, open Apps > Explore more apps, search for FourRealities and choose Get app. The app asks to read and write Jira work, to read users, to search your site's Confluence pages, to store its own data, and to report personal data to Atlassian. It calls no server outside your Atlassian site.
  2. Check the evidence sources (Jira administrator). Open Jira settings > Apps > FourRealities gate authority. The defaults detect DefinitionGuard, LedgerSeal and pull request data on their own (section 6).
  3. Connect code tools (optional). The Code gate reads the Jira Development field. Connect GitHub, Bitbucket or GitLab to Jira if you have not.
  4. Open the dashboard. In a project, open Four Realities in the project navigation. The first view builds the project's snapshot; after that it is rebuilt each day.

Updating to 3.0.0. FourRealities 3.0.0 adds evidence reports. It is a major version because it adds file storage, so a site administrator accepts the update in Manage apps before reports appear.

Licence. With an inactive licence the app shows "Licence not active" and makes no new evidence reports; existing evidence reports can still be viewed and downloaded.

3. The four gates and the RAI

GateQuestionEvidence that counts
IntentIs the work traced to a decision record?A remote link to a Confluence page on your site, or an issue link to an issue whose type is a decision type (default: adr, architecture decision, decision, decision record, spec, specification, requirement). Titles and keywords never count.
ProcessIs the Definition of Done complete?A DefinitionGuard record with a valid signature that says the checklist is complete. A Checklists for Jira (HeroCoders) checklist can be shown, but it cannot be verified, so at Done it counts as missing.
CodeWas the work merged through a pull request?A merged pull request in the Jira Development field. This is a heuristic: apps cannot read pull request approvals.
AuditIs the finished work sealed?A LedgerSeal record with a valid signature and the status SEAL_VALID. An issue that is still in a LedgerSeal approval route and not sealed yet counts as not sealed.

Gate states

  • Evidence found and Evidence missing are scored. A found state can add "(not verified)", "(heuristic)" or "(link only)" when FourRealities could not check the source fully.
  • Excepted: an approved Code exception. It is shown as evidenced in the readiness banner, but not scored in the RAI.
  • Needs re-check: the source was not read in this snapshot. Use Refresh.
  • Not applicable: the gate does not apply yet, for example Process and Audit before the issue is done, or Intent before work starts.
  • Not used on this site: an administrator turned the check off. It is not scored.

A DefinitionGuard or LedgerSeal record counts only when its signature is valid. An unsigned record, or one signed with an unknown key, counts as missing at Done. A record changed after signing, copied from another issue, or older than a record already seen counts as missing, also before Done.

Reality Alignment Index (RAI) and risk

RAI = found gates divided by (found + missing gates), times 100. With no scored gate, the issue is UNRATED. The risk level comes from the RAI: Low 85 or more, Medium 70 to 84, High 50 to 69, Critical below 50. A rework loop is a move from a Done status back to a status that is not done, or from In Progress back to To Do. Rework never changes a gate.

4. The project dashboard

Open Four Realities in the project navigation. The page has two tabs: Dashboard and Evidence reports.

Checks in useWhich sources this site uses, and which are not used.

Issue triage

Search by key or summary, and filter by Assignee, Sprint and Gate. The views My issues, Critical and high, Audit prep and Needs a decision link set filters in one click. Filters combine; Clear all filters keeps the search text. The table shows 25 rows per page.

Inspect opens the issue's gates with their sources. Use Previous issue and Next issue to step through the filtered rows, or Open issue.

The dashboard shows only the issues you can see in Jira. It reads at most 2,000 issues per project, newest first, and says so when it stops.

5. The issue panel: close the gaps

Open an issue. The Four Realities entry in the details column shows the chips, the alignment, the risk and See all findings. The full panel opens from the issue's app button.

Under the gate findings, Why N%? shows the parts of the score.

Link a decision record

  1. Choose Link decision record.
  2. Choose Search Confluence..., type at least 2 characters of the page title and choose Search. Choose Select on a result. Or type the Page address and a Page title (3 to 255 characters).
  3. Choose Add link.

Result: "Link added. Intent: Evidence found." FourRealities adds a Jira remote link as you; you need Edit issues. If FourRealities could not check the page, Intent reads "Evidence found (link only)". A link to a page outside your site is added, but Intent stays missing.

Request a Code exception

For done work that needs no pull request:

  1. Choose Request Code exception.
  2. Write the Reason (15 to 500 characters) and, if you want, Notes, such as a change ticket. Choose Save exception.
  3. A project administrator, a Jira administrator or a member of an approver group, who is neither the requester nor the assignee, opens Show details and chooses Approve exception or Reject exception.

Result: after approval, Code shows Excepted. Until then it stays Evidence missing. An approver can later Revoke exception with a reason; the requester can Withdraw request while it waits. A request is refused when a pull request is linked.

Other actions

  • Add rework reason appears in the Process findings when the issue has a rework loop. The reason never changes a gate.
  • Request retrospective review appears when Code is found with a merged pull request. It posts a comment (15 to 1,000 characters) on the issue as you.
  • When Process or Audit is missing, the next step names the Definition of Done panel (DefinitionGuard) or the Approval Seal panel (LedgerSeal). FourRealities never writes their records.

6. Site settings (Jira administrator)

Open Jira settings > Apps > FourRealities gate authority.

SettingChoices (default first)
Intent (decision records)In use; Not in use
Process (Definition of Done)Detect (DefinitionGuard, when a signed record is found); DefinitionGuard; Checklists for Jira (HeroCoders); Not in use
Code (pull requests from the Jira Development field)Detect (when pull request data is found); In use; Not in use. Code needs Jira's Development field, which Jira shows when a development tool such as Bitbucket, GitHub or GitLab is connected to the site. On a site with no Development field, Code is Not applicable on every issue whatever you choose: the page says so under the Code control, the choice reads "In use (no effect: this site has no Development field)", and the "Now:" line reads "Not applicable on this site (no Development field)".
Audit (approval seal)Detect (LedgerSeal, when a signed record is found); LedgerSeal; Not in use
Decision issue typesIssue type names, separated by commas. At most 20, each at most 60 characters.

Choose Save evidence sources. Result: "Saved. Dashboards build their snapshot again on the next view."

The Approver groups card names the groups whose members can approve, reject and revoke Code exceptions, besides project and Jira administrators. Search, Add, then Save changes. The Evidence reports card is described in section 7.

7. Evidence Reports for Change-Management Audits

For an auditor's sample, FourRealities makes an evidence report: for one project and one period, the issues in scope with their four checks, the DefinitionGuard and LedgerSeal records FourRealities verified, Code exceptions and rework reasons, and who changed which field and when, from Jira's history. An issue is in scope when it was created in the period or changed in it.

FourRealities is not an administrative audit log: Jira's audit log and Atlassian Guard keep it. A report holds what Jira's history held when it was made; an issue deleted before then is not in it.

Make a report

  1. Open the project, then Apps > Four Realities > Evidence reports, and choose New evidence report.
  2. Choose From and To (UTC). Both days are included. A report covers at most 366 days.
  3. If you want, choose at most 10 Fields and 10 People. Empty means all fields and everyone. People filters by who made the change.
  4. Choose Make report.

Project administrators, Jira administrators and members of an evidence report group can make reports. The report holds every change in the range that you can see. Result: "The report is queued. It appears here when it is ready." The row goes from Queued to Running to Ready, and the list refreshes on its own. A row can also read Failed with the reason, Expired or Deleted. A badge "N issues not in report" means some issues of the scope could not be read.

Schedules

Project and Jira administrators can add a weekly (Monday to Sunday, UTC) or monthly (calendar month, UTC) schedule. The report for a period is made the day after the period ends and stored in the app. It covers all the project's issues in scope, found by the app, because no user is present; a download still needs every issue in it to be visible to you. It is not sent anywhere.

In the Schedules card, choose the Cadence, and if you want Fields and People, then choose Add schedule. Remove deletes a schedule. A project has at most 5 schedules.

Download

Choose Download and save the four files: the report as JSON and as CSV, the signed manifest, and the people file. You can download a report only when you can see every issue in it. The people file is not signed: it names the people of the report as you can see them today.

When some issues of the scope are not in the report (deleted, no longer readable, or moved to another project while the report was made), the download window names each one with its key and the reason, 50 per page, with Previous and Next.

What a report shows

People appear as tokens in the signed files. Free-text fields (Summary, Description, Environment and text custom fields) show that they changed and the lengths, not the text. The checks are observed when the report is made, not at the time of each change. The report files hold, in plain text: each issue's key, type, status and current summary (up to 120 characters); who changed which field and when, with the old and new values of fields that are not free text; the reasons of Code exceptions; rework reasons and their notes; the address (URL) and title of a linked Confluence page, which users type and which can hold any text; the key and type of a linked decision issue, never its title or content; and evidence references: LedgerSeal certificate ids and hashes (such as the Definition of Done hash).

Check a report

FourRealities signs the manifest with Ed25519. Run the open verifier:

node verify-fourrealities-report.mjs <manifest.json> <report.json> <report.csv> [--previous <previous-manifest.json>]

A changed file fails the check. Each manifest names the previous report of the project, so a removed report shows as a break. See the open verifier guide.

Keeping and deleting

Reports are kept for 400 days unless a Jira administrator chooses 90 days to 7 years in Jira settings > Apps > FourRealities gate authority > Evidence reports. A shorter retention applies to existing reports from the next daily run. A Jira administrator can delete a report early with a reason (15 to 500 characters); a record of the deletion stays in its place. Reports are removed when their retention ends. Some small records outlive it: a deletion record (tombstone, with the administrator's reason) stays while the app is installed; the list entries of failed, expired and deleted reports stay until the newest 200 entries of the project push them out; and the link from each party token to an Atlassian account id stays while the account is open (it is reported to Atlassian every week, and removed when the account closes).

Limits

At most 10,000 issues, 366 days, 50 MB per file and 200 reports per project. A report that is too large is not stored, and the list says why. A project can have at most 3 reports waiting.

9. Data stored and where

  • Reads: Jira issue fields, the changelog, remote links, issue links, the Development field, and the issue properties of LedgerSeal, DefinitionGuard and Checklists for Jira. It searches the Confluence pages of your own site as you.
  • Storage: snapshots, Code exception events, rework reasons, site settings and evidence report records are kept in Atlassian Forge storage; evidence report files are kept in Atlassian Forge Object Store. Nothing is sent outside your Atlassian site.
  • On the issue: the issue property fourrealities-exception (the Code exception state and the latest rework note), and the remote links and comments users add.
  • Personal data: Atlassian account ids only where a rule needs them: who requested or decided a Code exception, who gave a rework reason, and the assignee, for the "My issues" filter. No names are stored. Evidence report files name people by a pseudonymous token. The ids are reported to Atlassian every week; closed accounts are erased and show as "a former user". The people file of a download is removed 24 to 25 hours after the download.
  • Retention: exception events and notes have no expiry. Reports follow the retention in section 7.

See the privacy policy.

10. Limits

  • The dashboard reads at most 2,000 issues per project, newest first. A first view has about 20 seconds; the daily snapshot reads the rest.
  • The trend keeps 52 weekly points and shows 4 weeks. The weekly change needs at least 10 rated issues in both weeks.
  • Up to 500 projects take part in the daily run.
  • Reasons: 15 to 500 characters. Notes: up to 1,000. Review comment: 15 to 1,000. Link title: 3 to 255.
  • Confluence search: at least 2 characters, at most 10 results.
  • Evidence reports: see section 7.

12. Uninstall and data removal

  1. Download any evidence reports you must keep.
  2. A Jira administrator opens Jira settings > Apps > Manage apps and uninstalls FourRealities.
  3. Atlassian keeps the app's Forge storage for 28 days and then deletes it: snapshots, exception events, rework reasons, settings and report records.
  4. The issue property fourrealities-exception, and the links and comments users added, stay in Jira.

For other requests, write to privacy@asymm.systems.
