FourRealities Guide

FourRealities User & Administrator Guide

How to measure cross-reality delivery alignment, calculate the Reality Alignment Index (RAI), detect unproductive rework loops, and resolve architectural drift between Confluence specs, Jira issues, and Git pull requests.

1. The Disjoint Realities Problem

Software development in modern organizations takes place across four distinct, disconnected realities:

  1. Intent (The Architecture): Architectural Decision Records (ADRs), requirement specifications, and API contracts authored in Confluence.
  2. Process (The Tracking): Sprints, tasks, epics, estimations, and workflow transitions in Jira Cloud.
  3. Code (The Implementation): Git branches, commits, pull requests, and CI/CD runs in GitHub, GitLab, or Bitbucket.
  4. Audit (The Reality): Actual deployment history, changelogs, operational telemetry, and activity logs.

In standard teams, these four realities diverge quickly. Code is merged that contradicts Confluence specs; Jira tickets are marked Done while pull requests remain open; and tickets bounce back and forth between In Review and In Progress without management visibility. FourRealities reconciles all four perspectives into an objective delivery integrity score.

2. The Reality Alignment Index (RAI)

FourRealities evaluates every project and issue against an objective 0 to 100 Reality Alignment Index (RAI):

  • 90 - 100 (Optimal Alignment): Code matches specifications, Jira statuses reflect active Git branch states, and no unresolved rework loops exist.
  • 70 - 89 (Moderate Drift): Minor discrepancies detected (e.g. PR merged but ticket pending transition, or remote links missing).
  • Below 70 (Severe Drift): Code merged without specification links, tickets marked Done with open PRs, or multiple rework cycles detected.

3. Rework Loop Detection & Bounce Alerts

One of the largest hidden costs in software engineering is the rework loop: issues repeatedly rejected by QA or code review, bouncing between In Review and In Progress. Standard Jira burndown charts treat reopened tickets the same as newly started work.

FourRealities monitors workflow oscillation:

  • Flags any issue that transitions backwards through the workflow two or more times.
  • Calculates rework cycle time and engineering effort lost to ambiguous requirements or unstable code.
  • Triggers an amber or red alert lozenge on the Jira issue panel to prompt architectural triage.

4. Zero-Egress Connectivity & Settings

Unlike third-party analytics platforms, FourRealities operates with zero external network egress. It does not make outbound HTTP requests to external Git or Confluence APIs:

  • Confluence Integration: Reads Jira native remote links connecting issues to Confluence pages within your tenant.
  • Git Integration: Reads Jira native Development Information (dev-status) populated by your existing GitHub, Bitbucket, or GitLab Jira integrations.
  • Administration: Configure alignment weightings and rework thresholds under Project Settings > FourRealities.

5. Resolving Drift & Remediation Workflow

When an issue displays low RAI scoring or drift warnings:

  1. Click Show Drift Breakdown on the issue panel.
  2. Inspect which reality failed alignment (e.g. Intent: Missing Confluence Spec Link or Code: Unmerged Pull Request).
  3. Link the missing architectural artifact or complete the code review.
  4. Click Re-calculate Alignment. The RAI updates immediately, restoring healthy project delivery metrics.
